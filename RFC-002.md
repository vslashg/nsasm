# RFC 002

Generalizing nsasm beyond the SNES: bus addresses, storage addresses, and
mapped memory

Supersedes RFC-001.

## Problem

nsasm is SNES-specific and 65816-specific.  We want to support other
6502-family environments — in particular the NES (with mapper chip carts) and
the Famicom Disk System — without giving up the toolchain's core design: a
shared abstract-interpretation engine driving both assembly and disassembly.

The single `Address` type is the main obstacle.  It currently serves every
address-shaped role in the codebase, which works only because of a
SNES-specific accident described below.

## Three concepts, not two

RFC-001 proposed a two-way split into "logical" and "physical" addresses.
Working through the NES and FDS cases shows there are actually three distinct
concepts currently squashed into `Address`:

1. **Operand shape** — how an address is rendered in an instruction encoding:
   zero-page byte, 16-bit word, 24-bit long.  This is a property of the *use
   site*, not of an address.  It is already largely modeled by addressing
   modes and `NumericType`; the `<` and `@` prefixes select it.

2. **Bus address** — what the CPU emits on its address pins.  24 bits on the
   65816, 16 bits on the NES's 6502.  This is the space where the PC lives,
   where branch targets are computed, and where hardware registers exist.
   NES `$2000` is PPUCTRL, full stop: it has an address but no *contents*.

3. **Storage address** — the durable identity of a byte: (PRG ROM chip,
   offset), (FDS file, offset), (work RAM, offset).  This is the space in
   which disassembly coverage, `ranges.h`, ROM patching, and labels-on-code
   operate.  Some storage (RAM) has no persistent contents; MMIO has a bus
   address but no storage at all.

A single `Address` type has sufficed so far only because LoROM and HiROM are
*static* mappings: bus address and storage address are interchangeable via
the pure function `SnesToROMAddress()`.  On an MMC1 cart that function stops
being pure — bus address `$9000` refers to different ROM bytes depending on
what was last written to the bank register, and the same ROM byte may appear
at two different bus addresses.  The FDS goes further: the mapping is
established by load *events*, and one file can be loaded over another.

The generalization is therefore not "add a second address type."  It is:
**the relation between bus and storage becomes a function of machine state.**

## Core types

### `BusAddress`

A per-target-width value type.  The 65816 flavor is (bank, 16-bit address)
with the existing wrapped-arithmetic rules; the NES flavor is a plain 16-bit
value.  The PC is a `BusAddress`.  Relative-branch arithmetic happens here.

### `StorageAddress`

A (region id, offset) pair.  Regions are declared per cartridge (see the
layout file below) and carry attributes: backed by the ROM image or not,
readable/writable, MMIO.  Region ids give names to things that are not
usefully numbers — individual PRG banks, FDS files, the hardware register
block — without the address type itself becoming exotic.

Arithmetic is type-checked: subtracting two storage addresses in the same
region yields an offset; subtracting across regions is an error.

### `LabelValue`

Becomes a real sum type: **Number | BusAddress | StorageAddress**, replacing
the current int-that-might-be-an-address.

- A `label:` on placed code or data binds to a *storage* address.
- A declared hardware register or RAM variable binds to a *bus* address.
- A plain constant is a number.

Using a storage-valued label as an operand requires rendering it as a bus
address, which requires a mapping, which may require a state assumption.  The
C++ type system enforces the design during migration.

## The mapping layer

### `MemoryModel`

A per-target interface mediating between the two address spaces:

```
ErrorOr<StorageAddress> BusToStorage(BusAddress, const SystemState&);
ErrorOr<BusAddressSet>  StorageToBus(StorageAddress, const SystemState&);
```

Both are fallible.  `StorageToBus` is set-valued: NES mirroring, or a bank
mappable into either window, can put one byte at several bus addresses.
SNES LoROM/HiROM ignore the state argument entirely — the current
`SnesToROMAddress()` becomes the trivial instantiation.

### `SystemState`

Per-console machine state that affects mapping, tracked with the same
abstract-value machinery as CPU flags:

- SNES: empty.
- MMC1/MMC3: the bank registers, each in the known / original / unknown
  domain used by `RegisterValue`, with join-at-merge.
- FDS: the set of currently loaded files — structurally closer to the `Stack`
  model: a structured abstraction that is *abandoned* when analysis loses the
  thread.

This is the deliberate centerpiece of the design.  Mapper state is the same
kind of problem as the M bit:

- A write to a bank register changes how subsequent operands resolve, just as
  `REP #$20` changes how subsequent immediates decode.
- An unknown bank register means "cannot follow this jump through the
  switchable window" — the same failure class as "cannot size this
  immediate."  It fails the same way, is annotated the same way, and merges
  at control-flow joins the same way.

### `ExecutionState` split

`ExecutionState` becomes the composition of:

- **`CpuState`** — per-ISA: flags, registers, the stack model.  The 6502
  version is strictly simpler (no E/M/X bits, no variable-size immediates,
  so instruction sizing is never ambiguous).
- **`SystemState`** — per-console, as above.

`Instruction::Execute()` gains a hook through the `MemoryModel`: "does a
write to this bus address mutate system state?"  On MMC1, `STA $8000` is
simultaneously a store and a state-tracking event.

## Disassembler changes

The worklist and all output maps are re-keyed from bus addresses to
**storage** addresses, with the bus-space PC carried alongside the
`ExecutionState`:

- Two paths reaching the same *storage* byte merge their states.
- Two paths reaching the same *bus* address under different mapper states are
  **different code** and must not merge.

On the SNES this distinction was invisible.  It is the single most
behavior-significant change in the design.

Branch and jump targets are computed in bus space, then translated to storage
via the current `SystemState`.  If the relevant mapping is unknown, the
disassembler stops with an error at that site — the same philosophy as
refusing to decode an immediate under an unknown M bit — and the user
supplies an assumption (below).

## Syntax

The guiding move is cc65's separation between *what the code is* (source,
segments) and *where it lives* (a per-project config), adapted to nsasm's
identity as a patching toolchain rather than a from-scratch linker.  nsasm
keeps fixed addresses and local readability; there is no relocation.

### 1. Target/layout file

A per-project file (analogous to ld65's `.cfg`) declaring the machine and its
regions:

```
machine nes
mapper  mmc1
region  prg0  storage=prg_rom[0x00000:0x04000]  window=$8000, $C000
region  prg7  storage=prg_rom[0x1C000:0x20000]  window=$C000  fixed
region  ram   bus=$0000:$0800
region  hw    bus=$2000:$4020  mmio
```

This replaces the header-sniffed LoROM/HiROM enum, names the storage regions
(PRG banks, FDS files), and gives the disassembler its vocabulary for output.
Exact grammar TBD; ld65's config is the model to deviate from knowingly.

### 2. Placement names the region

Today `.org $c08000` works because a SNES bus address is unambiguous.  On the
NES, `.org $8000` is meaningless alone — *which bank?*  Placement becomes two
coordinates:

```
.segment "prg3"
.org $8000        ; this code assumes it is mapped at $8000
```

For SNES sources, `.org $c08000` alone remains valid sugar, since the region
is derivable from the bus address.  Existing SNES sources keep working.

### 3. State assumptions generalize `.mode`

`.mode` already lets the programmer assert flag state; the mapper analogue is
an `.assume` directive (naming chosen to echo ca65):

```
.assume prg_lo = prg3
```

`.entry` grows to carry system state alongside flag state.  This annotation
path is *load-bearing*, not a corner case: real NES games load bank numbers
from tables, which sends the abstract bank registers to unknown constantly.
The human rescues the analysis at those points, exactly as `.mode` rescues
flag tracking today.

### 4. Adopt ca65's `=` / `:=`, retire `.equ`

The syntax-level reflection of the `LabelValue` sum type:

- `FOO = 4` — a number.  No address semantics.
- `PPUCTRL := $2000` — a *bus address*.  Hardware registers are declared this
  way, plausibly in shippable per-machine include files.
- `label:` — a *storage address* on placed code or data.

### 5. Rendering prefixes keep their contract

Retained from RFC-001, generalized: a prefix is a **rendering contract with
an assertion, not a value transformation**.  All forms hold the same
underlying address; the prefix selects the operand shape and the assembler
enforces reachability at encode time.

- `label` (no prefix): 16-bit operand.  Assertion generalizes from "same bank
  as PC" to "reachable at a 16-bit bus address under the current
  `SystemState` mapping."
- `<label`: zero-page/direct-page 8-bit operand, with the matching assertion.
- `@label`: 24-bit long operand.  65816 only.

Also retained from RFC-001: the `>` (high byte) and `^` (bank byte) operators
are removed in favor of named functions (`high_byte()`, `bank_byte()`).
Extracting numeric bytes from an address for immediate operands is a
different operation from rendering an address, and conflating them is what
made the single-type model muddy.

## Code layout

Target dependency shape:

```
nsasm/core:    error, location, expression, numeric_type, token, parse
               bus_address.h, storage_address.h, region.h   (target-agnostic)
               memory_model.h (interface)
               cpu_state / system_state interfaces + shared abstract-domain kit
nsasm/isa:     mnemonic, addressing_mode, opcode_map, instruction, decode
               — parameterized by an Isa (6502 / 65c02 / 65816 tables)
nsasm/target:  snes_lorom, snes_hirom, nes_nrom, nes_mmc1, fds
               — each = MemoryModel + SystemState + image loader
nsasm/asm:     directive, module, assembler  (segment/region aware)
nsasm/dis:     disassemble  (worklist keyed by storage address)
```

A `Target` object bundling {Isa, MemoryModel, image format} is threaded
through `Assembler` and `Disassembler`.  Virtual dispatch everywhere the
target varies; per the project's stated principles, efficiency does not
matter, so we do not template the world.

`InputSource` / `OutputSink` are re-keyed on storage addresses.  The
bus-to-storage translation happens in the assembler/disassembler layer, not
inside the image class.

## Migration

Staged so every commit is green, with `RomIdentityTest` as the harness:

1. **Type split under SNES-only.**  Introduce `BusAddress` and
   `StorageAddress`; re-key `InputSource`/`OutputSink` and `ranges.h` on
   storage; make LoROM/HiROM the trivial `MemoryModel`.  No syntax changes;
   bit-identical output.
2. **State plumbing.**  Split `ExecutionState` into `CpuState` +
   `SystemState` (empty for SNES); add the write hook to `Execute()`.
3. **Syntax changes, still SNES.**  Layout file, `.segment`, `=`/`:=`, retire
   `.equ`, remove `>`/`^`.  This is the one backward-incompatible release —
   done while there is a single target, so NES support later is additive
   rather than a second breaking change.
4. **6502 ISA + NROM** (mapperless NES).  Exercises the 16-bit bus, MMIO
   regions, and per-ISA opcode tables with *no* dynamic mapping, isolating
   ISA work from mapper work.
5. **MMC1/MMC3, then FDS.**  The genuinely novel analysis (abstract mapper
   state, load events) lands last, on settled foundations.

## Open problems

- **Set-valued `StorageToBus`.**  When a bank is visible at two windows,
  which bus address does a plain `label` render as?  Proposed rule: whichever
  window the current `SystemState` proves; otherwise error and ask for an
  `.assume`.  This will produce real annotation burden in real games.
- **Annotation ergonomics for disassembly.**  How `.assume`-style facts
  attach to a disassembly in progress (side file? iterative re-runs?) is a UX
  question as large as the type system.  Prototype early against a real MMC1
  game rather than trusting it on paper.
- **RAM labels.**  Variables in RAM have bus addresses but no storage
  contents.  cc65 handles this with bss-type segments; nsasm needs some way
  to declare "label at bus address, N bytes reserved" that participates in
  the region system.
- **FDS load semantics** stretch the model furthest — mapping changes by load
  event, not register write.  Deliberately under-designed here; FDS is the
  test of whether `SystemState` is genuinely general or secretly
  mapper-shaped.  Do not design it in detail until MMC1 works.

## Summary

Keep the abstract-interpretation engine — it is the crown jewel, and it
generalizes cleanly to mapper state.  Split `Address` into bus vs. storage,
with the mapping mediated by tracked system state.  Take from cc65 the
segment/region separation and the `=`/`:=` value-vs-address distinction.
Keep nsasm's soul: fixed addresses, local readability, no linker relocation
games.
