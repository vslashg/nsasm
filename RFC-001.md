# RFC 001

Address types

## Problem

The code is too SNES-specific, and too 65816-specific.

## Idea

Splitting `Address` into two types, `LogicalAddress` and `PhysicalAddress`, will
enable extending to other 6502-family processors and other consoles.

A `LogicalAddress` is an address as it is expressed in machine language.  These
are typed: in 65816, these could be a zero page address, a normal 16-bit
address, or a long 24-bit address.

A `PhysicalAddress` is a conceptually "physical" address in the 65816 address
space.  For a 65816, this is a 24-bit address, probably represented as an 8-bit
bank and a 16-bit address.

A `LogicalAddress` can be converted to a `PhysicalAddress` through an
`ExecutionState`, as it knows the current bank, for example.

In a future where we support 8-bit NES games, the `ExecutionState` can grow to
understand NES mapper chip mapping schemes: here a `LogicalAddress` is the
address after all mapper extensions to the address space are applied.

## Expression model

Expressions already carry a `NumericType` (`T_byte`, `T_word`, `T_long`).
Under this RFC, labels — which refer to physical addresses — carry a distinct
physical-address flavor in the type system.  The rendering prefix at a use site
controls how the physical address is converted to a logical one for encoding.

The three rendering prefixes are:

- `label` (no prefix): renders as a 16-bit logical address (`T_word`).  Asserts
  the label is in the same bank as the current PC; emits a 2-byte operand;
  selects `A_dir_w` addressing.
- `<label`: renders as an 8-bit logical address (`T_byte`).  Asserts the label
  is in bank 0 (zero page); emits a 1-byte operand; selects `A_dir_b`
  addressing.
- `@label`: renders as a 24-bit logical address (`T_long`).  Always valid;
  emits a 3-byte operand; selects `A_dir_l` addressing.

Crucially, all three forms hold the same underlying 24-bit physical address
value.  The prefix does not extract or transform the value — it annotates the
rendering contract, and the assembler enforces the constraint at encode time.

Literals, by contrast, are already logical.  `$04` is `T_byte` and means *the
number 4*; no physical address is involved and no rendering assertion is
required.  In summary:

| Expression | Type           | Meaning                                      |
| ---------- | -------------- | -------------------------------------------- |
| `$04`      | `T_byte`       | literal logical value 4                      |
| `$0004`    | `T_word`       | literal logical value 4, 16-bit              |
| `label`    | `T_word` (physical) | physical addr, render as 16-bit         |
| `<label`   | `T_byte` (physical) | physical addr, render as 8-bit          |
| `@label`   | `T_long` (physical) | physical addr, render as 24-bit         |

Whether the physical flavor is a separate type dimension or a flag on the
existing `NumericType` variants is an implementation detail to be resolved
during migration.

The `>` (high byte) and `^` (bank byte) operators are removed.  They extracted
numeric bytes from a physical address for use in immediate operands, which is a
different use case from rendering a physical address as a logical one.  They
will be replaced by named functions (e.g. `high_byte()`, `bank_byte()`) in a
future change.

## Migration

This is going to require being clear, at each point in code, when we are dealing
with a physical or logical address.  Type safety in C++ will probably help
incrementally doing this work.

The mechanical first step is renaming `Address` to `PhysicalAddress` throughout
the codebase.  Most existing uses of `Address` are already physical; the narrow
set of conversion sites (relative branch arithmetic, far-jump target resolution)
are where the logical/physical boundary will need explicit handling.
